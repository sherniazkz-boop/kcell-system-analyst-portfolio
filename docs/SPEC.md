# Короткое ТЗ · заявка на подключение услуги

**Цель.** Пользователь может создать демонстрационную заявку, получить её номер и по этому номеру посмотреть текущий статус. Данные вымышленные. В сценарий входят форма, два API-метода и хранение в SQLite. Фактическое подключение услуги и изменение статуса оператором находятся за рамками демо.

## Требования и приёмка

| ID | Требование | Критерий приёмки |
| --- | --- | --- |
| REQ-1 | Создание заявки по псевдониму и услуге. Псевдоним содержит 1–60 печатных символов после удаления пробелов по краям. Варианты услуги — `home_internet` и `esim`. | Валидный JSON добавляет одну строку. Ответ `201` содержит номер UUID, код услуги, статус `RECEIVED` и время в UTC. Заголовок `Location` указывает на ресурс заявки. |
| REQ-2 | Обязательные поля проверяются на сервере. Интерфейс выводит полученные ошибки рядом с полями. | Пустое, отсутствующее или недопустимое поле даёт `422` и запись в `error.fields`. Количество строк в БД прежнее. |
| REQ-3 | Просмотр статуса по номеру заявки. | Для существующего UUID возвращается `200` с текущим статусом, для неизвестного UUID — `404`, для номера неверного формата — `400`. Ответ содержит номер, услугу, статус и время создания. |
| REQ-4 | Сохранение заявки в SQLite. | После перезапуска с тем же файлом прежний номер по-прежнему находится. |

## Данные и API

В таблице `applications` хранятся `id` (первичный ключ), `applicant_alias`, `service_type`, `status` и `created_at`. Новые заявки получают `RECEIVED` («Принята»). При запуске добавляются две демонстрационные записи со статусами `IN_REVIEW` («На рассмотрении») и `CONNECTED` («Подключена»). Запрос статуса читает сохранённое значение.

| Метод и маршрут | Тело запроса | Ответы |
| --- | --- | --- |
| `POST /api/applications` | JSON-объект с `applicant_alias` и `service_type` | `201`, `400 INVALID_JSON`, `413 BODY_TOO_LARGE` свыше 8 КиБ, `415 UNSUPPORTED_MEDIA_TYPE`, `422 VALIDATION_ERROR`. |
| `GET /api/applications/{id}` | Без тела | `200`, `400 INVALID_ID`, `404 APPLICATION_NOT_FOUND`. |

Тело ошибки содержит `error.code` и `error.message`. Ответ `422` дополнительно содержит объект `error.fields`, где ключ совпадает с именем поля формы. Псевдоним сохраняется для записи и исключён из публичной структуры ответа демо.

## Декомпозиция

| Команда | Задача | Связь с требованиями |
| --- | --- | --- |
| Frontend | Сделать форму, отправить JSON и показать номер новой заявки. Подставить номер в форму поиска. | REQ-1 |
| Frontend | Связать `error.fields` с полями формы и перевести фокус на первое поле с ошибкой. | REQ-2 |
| Frontend | Сделать форму поиска и показать результат или сообщение API. Перевести коды статусов в подписи. | REQ-3 |
| Backend | Создать таблицу SQLite, ограничить набор статусов и подготовить демонстрационные строки. | REQ-1, REQ-4 |
| Backend | Разобрать JSON, проверить поля, сформировать ответ `422` или сохранить заявку и вернуть `201`. | REQ-1, REQ-2 |
| Backend | Реализовать чтение по UUID и согласовать поля ответа с frontend. | REQ-3, REQ-4 |
| Backend | Проверить контракт HTTP, запись в SQLite и SQL-агрегацию по статусам. | REQ-1–REQ-4 |

Согласованный JSON-контракт позволяет сделать форму и backend параллельно. Интеграционная приёмка проверяет, что номер из ответа `POST` находится через `GET`, а при `422` новая строка отсутствует.
